# 需求规范 (Product Specification)

> **功能名称：** Tkinter 双摄快速首屏性能优化
> **版本：** v1.0
> **状态：** 已批准（待工具冻结）
> **作者：** Codex + 用户
> **最后更新：** 2026-07-10

---

## 1. 概述

当前 Tkinter 双摄会话在点击“开始”后，需要同步打开第二摄像头，并串行读取两路首帧；开启“录像写入骨架”时，还要在任何画面出现前串行创建两条 MediaPipe VIDEO pipeline。该功能要把摄像头冷启动和首帧读取前移到选择阶段，在不改变正式评分、录像内容和文件 VIDEO 行为的前提下，让双路画面快速、同时出现。

---

## 2. Analyze Requirements / 需求分析结论

- **歧义检查：** “首屏”定义为用户点击“开始”后，Tk 主线程在同一次回调中把正面和侧面两张有效摄像头帧配置到两个预览 Label；不以队列入队或单路先出现作为完成。“预热完成”定义为两路角色均持有已打开的 capture 和持续更新的有效最新帧。
- **冲突检查：** 用户要求两路必须同时出现，因此不采用逐路渐进显示；用户允许开始前两台摄像头已打开并持续读取，解决了隐私/资源占用与低延迟之间的取舍。骨架加载期允许裸帧过渡，但裸帧不得进入骨架录像。
- **遗漏边界：** 必须覆盖第二摄像头未选择、两路选中同一设备、预热进行中点击开始、单路打开/读帧失败、5 秒超时、模型初始化失败、启动期停止/关窗、快速重启、视频文件切换和摄像头刷新。
- **Intake 未决项归类：** MediaPipe 0.10.35 和 GPU 不作为既定实现；仅在隔离 A/B 达到预注册阈值后才允许修改版本锁或新增 GPU 实验开关。
- **并发 / 数据 / 安全风险：** 预热线程、正式 worker 和 Tk 主线程共享 capture 所有权与最新帧；必须用 role generation、停止事件和原子所有权转移防止旧线程泄漏或晚到帧复活。预览帧只驻留内存，不新增持久化、网络或敏感数据出口。
- **Quick Plan 跳过原因：** n/a；采用 strict workflow。

## 3. Intake Handoff / 澄清交接

- **Status:** complete
- **Confirmed facts:** 当前主要问题发生在双摄模式；骨架关闭和开启都慢。第二摄像头没有预打开，双路首次 `read()` 串行；骨架开启时两条 pipeline 在出图前串行创建。本机现有模型构造和首推约 0.1-0.2 秒，摄像头启动/首帧更可能是主瓶颈。
- **Scope:** Tkinter 双摄角色预热、最新帧维护、首帧原子配对、裸帧到骨架帧过渡、录制就绪门禁、启动时序指标、相关测试，以及 MediaPipe 0.10.35/GPU 的门控 A/B。
- **Non-goals:** 不修改 Vue/Tauri、文件 VIDEO、模板提取、正式评分、`pose33_v3`、YOLO 路由、默认模型档位、手部检测默认值或正式运行阶段的双摄采集语义。
- **Decision boundaries:** 可新增独立 Python 摄像头预热 helper；两路首帧必须原子交付；骨架加载期间录制保持禁用。依赖升级和 GPU UI 必须服从预注册性能门槛。
- **Success criteria:** 预热完成时点击开始到双路实际 Tk 渲染 P95 <= 0.5 秒；冷启动不重复打开设备且等待不再是两路串行总和；停止/失败无资源泄漏、晚到帧或裸帧写盘。
- **Assumptions:** 两台摄像头选择后允许提前打开并持续读取最新帧；等待双路就绪上限为 5 秒；超时整体失败，不显示单路残留。
- **Risks:** OpenCV capture 取消/所有权转移、双路非原子 UI 更新、旧会话 generation、pipeline 构造期停止和依赖版本兼容性。

## 4. 用户故事与验收标准

### US-001: 双摄快速同步首屏

**作为** Tkinter 双摄用户，**我希望** 点击开始后正面和侧面画面快速同时出现，**以便** 不再面对长时间空白预览。

#### 验收标准

- **AC-001.1:**
  - **GIVEN** 正面和侧面摄像头均已在后台预热并持有有效最新帧
  - **WHEN** 用户点击“开始”
  - **THEN** 两路帧通过同一个双帧队列项交付，并在同一次 Tk 回调中渲染，20 次实机启动的 P95 不超过 0.5 秒

- **AC-001.2:**
  - **GIVEN** 一路或两路预热仍在进行
  - **WHEN** 用户点击“开始”
  - **THEN** 会话复用正在进行的任务或并发启动缺失任务，不得对同一 index 重复 `open_camera()`，总等待由较慢一路决定而非两路串行相加

- **AC-001.3:**
  - **GIVEN** 任一路在 5 秒内无法打开或产出有效帧
  - **WHEN** 启动等待结束
  - **THEN** 整体启动失败、释放两路资源、显示结构化状态，不显示单路残留画面且 `_post_done()` 恰好执行一次

### US-002: 骨架加载期间保持实时画面

**作为** 开启双摄骨架录像的用户，**我希望** 模型加载期间先看到同步裸帧，**以便** 模型初始化不会造成黑屏。

#### 验收标准

- **AC-002.1:**
  - **GIVEN** 双路最新帧已就绪且骨架开关开启
  - **WHEN** 正式 worker 串行创建两条 VIDEO pipeline
  - **THEN** 裸帧泵持续以 latest-wins 方式原子发布双帧，pipeline 全部就绪后停止裸帧泵并同时切换到骨架帧

- **AC-002.2:**
  - **GIVEN** 当前仍处于裸帧过渡阶段
  - **WHEN** 用户查看录制控件或底层 writer
  - **THEN** 录制按钮保持禁用，`write_frame` / `_write_recording_pair` 不接收任何过渡裸帧

- **AC-002.3:**
  - **GIVEN** 模型初始化期间发生停止、关窗或任一 pipeline 构造失败
  - **WHEN** 会话收敛
  - **THEN** 已创建的 pipeline、预热线程、capture 和录制状态全部释放，旧 generation 的帧不能进入当前 UI

### US-003: 以证据决定 MediaPipe 升级和 GPU UI

**作为** 维护者，**我希望** 通过隔离 A/B 判断 0.10.35 和 GPU 是否真正改善相关链路，**以便** 不把无收益的依赖或开关带入生产 UI。

#### 验收标准

- **AC-003.1:**
  - **GIVEN** 0.10.31 基线与隔离的 0.10.35 环境使用相同样本、模型和 benchmark 参数
  - **WHEN** 比较初始化、首个标注帧、P90/P99、FPS 和内存
  - **THEN** 只有相关指标至少改善 10%、其他关键指标退化不超过 5% 且回归全绿时才修改 `requirements.txt`

- **AC-003.2:**
  - **GIVEN** 0.10.35 在 Windows 上可请求 GPU
  - **WHEN** 运行现有多样本端到端 benchmark
  - **THEN** 只有 `active=gpu`，pose-only 相对 CPU >=1.30x、pose+hands >=1.20x 时才允许新增 Tkinter GPU 实验开关；否则保持 CPU 默认且不新增控件

## 5. 非功能性需求

| ID | 类别 | 描述 | 目标指标 |
|:---|:---|:---|:---|
| NFR-001 | 性能 | 预热完成后的双路首屏 | 20 次实机启动 P95 <= 0.5 秒 |
| NFR-002 | 并发 | 双路启动不得串行叠加冷启动，也不得重复打开同一设备 | 延迟注入测试证明总时长接近较慢一路；open 次数每 role/index 至多一次 |
| NFR-003 | 生命周期 | 启动期停止、关窗、失败和快速重启必须有界收敛 | 无活动 worker/capture 泄漏；旧 generation 帧计数为 0 |
| NFR-004 | 兼容性 | 默认评分、文件、模板与前端路径不漂移 | golden、valid_mask、现有 Tkinter/MediaPipe 契约全绿 |
| NFR-005 | 内存 | 每个 role 只保留一张最新帧 | 不建立无界帧历史或队列 |

## 6. 约束与假设

### 约束
- Tkinter 控件只在主线程更新；worker 不读取 Tk Variable。
- MediaPipe VIDEO pipeline 必须由正式 worker 构造和使用，不跨线程转移。
- 双帧首次显示和后续过渡显示必须使用一个单槽 pair queue，在同一次 `_tick` 中更新。
- 过渡裸帧不进入录像、在线评分或模板链路。
- 预热 capture 的取消、替换和转移必须保留 generation 防护。

### 假设
- 用户接受两台摄像头在点击开始前已打开、指示灯已亮，并持续读取 latest frame。
- 两台设备均可被现有 `open_camera()` 打开，设备驱动允许预热线程创建、正式 worker 后续使用。
- 真实双摄 P95 验收需要接入物理设备；无设备环境用确定性延迟注入验证并发结构。
